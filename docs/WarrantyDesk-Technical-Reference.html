§1 Scope of v1

WarrantyDesk covers the customer half of the warranty lifecycle. A buyer's order produces a warranty record per unit; the customer registers that warranty in a chat; later they return to the same conversation to file a claim, check its progress, and book a collection slot.

In scope

  • Warranty records created automatically at order activation, one per unit ordered
  • A QR code emailed per serial that opens Apple Messages with the registration message pre-filled
  • Conversational registration with identity verification against the order
  • Conversational claim intake with defect classification and a mandatory description
  • Claim status lookup and pickup slot booking
  • Escalation to a human through Omni-Channel

Deliberately out of scope for v1

  • The rep / approver side. The data model supports it — Claim_Stage__c has the approval states — but no approval process, decision UI or outbound notification flow is built.
  • The storefront. Orders are seeded by API. §17 covers what changes when the Experience Cloud site arrives.
  • WhatsApp. Dropped entirely, and that decision removed a component — see below.

The Apple-only decision and what it removed

The original design was WhatsApp-first with Apple as a second channel, which required a public /w/{serial} redirect page on an Experience Cloud site whose only job was user-agent sniffing: iPhone to the Apple deep link, Android to wa.me.

With one channel there is nothing to branch on. The QR encodes the Apple deep link directly, which deletes a public guest-access page, its controller, and the Experience Cloud site as a dependency of the entry point. Two further consequences:

  • No 24-hour session window. WhatsApp requires a pre-approved template to message a customer more than 24 hours after their last message. Apple has no such rule, so the notification path needs no template registry and no branch. Apple forbids business-initiated conversations outright, but every WarrantyDesk thread starts with the customer scanning a QR, so a thread always already exists.
  • Richer native controls. Apple's Quick Reply, List Picker and Time Picker are better primitives than WhatsApp's three-button reply. The Time Picker returns a real timestamp, which is why Pickup_Slot__c is a DateTime rather than a picklist of canned windows.

The principle that runs through everything

Every business rule is enforced twice: declaratively in the agent script via available when, and again server-side in Apex. The script guard shapes what the reasoning engine will consider; the Apex guard is what holds when a customer talks past it. Neither is decorative, and §13 shows what happened each time only one of them existed.

Identity, and why registration never creates it

The order was placed by a known customer, so an Asset is born already linked to a Contact and Account. Registration is a verify-and-flip, never a create: the agent collects a name and email and checks them against the Contact already on the record. A mismatch does not create a second Contact — it refuses and escalates. That is what stops a stranger who photographs someone else's carton from registering the warranty to themselves.

In the live channel, identity is free: MessagingEndUser.ContactId resolves the customer from their Apple ID without asking. Email is the fallback for any context with no messaging session — which includes Agentforce Builder preview, and that turned out to matter (§13).

§3 Data model

Seven custom fields across three standard objects. No custom objects were created. Asset already models "a specific unit a specific customer owns"; Case already models "a request with a lifecycle, an owner and an approval path". Inventing Warranty__c and Claim__c would have bought nothing and cost every standard feature that hangs off those objects — Omni-Channel routing, approvals, entitlements, the Service Console.

Known gap: serial uniqueness

Asset.SerialNumber is a standard field with no unique attribute available. Uniqueness is enforced only by construction — the serial derives from OrderNumber plus a sequence, and the trigger de-duplicates against existing serials on the same order. A manually created Asset could still collide.

§4 Record type

A Warranty_Claim record type exists on Case (012aj00000Dk9VRAAZ, active) so warranty claims separate cleanly from ordinary support cases in list views, page layouts and the future approval queue.

It has no business process attached, which is unusual for Case and worth recording. The Tooling API refuses to create a Case record type without one, but the standard REST endpoint POST /sobjects/RecordType does not — it accepted SobjectType, DeveloperName, Name and Description and produced an active record type with BusinessProcessId = null. Case Status simply offers its full picklist rather than a filtered subset. A support process can be added later without disturbing anything built on it.

Outstanding: profile visibility

The record type is not visible to any profile, so Case.RecordTypeId on filed claims is currently null. Granting visibility needs a Metadata API Profile deploy, which this org's headless bridge refuses (§14).

The code anticipates this. WarrantyDesk.claimRecordTypeId() calls isAvailable() and returns null when the running user cannot see the record type; CreateWarrantyClaimAction sets RecordTypeId only when a non-null id comes back. Claims file correctly today and start carrying the record type the moment visibility is granted — no redeploy, no code change.

§5 Apex layer

Eight classes and one trigger. Six of the classes are agent actions, one is a shared helper, one is the order-activation service.

All are without sharing. This is a considered choice: the agent acts on behalf of the customer who owns the record, and record-level sharing rules written for internal users would hide a customer's own asset from the agent user. Authorisation is enforced in the action logic instead — a claim can only be filed against an asset that passes warrantyActive, and registration only proceeds when the supplied identity matches the Contact already on the order.

Each action class holds exactly one @InvocableMethod — an Apex constraint, one per class — and returns a Result carrying not just data but a message field written for the agent, not the customer. That field tells the reasoning engine what to do next in plain language ("Do not file a claim. Offer paid repair options instead."). It is the main mechanism keeping the agent from improvising when an action refuses.

The six agent actions

CheckSerialRegistrationActionRead only

called by → subagent registration, action check_serial, gated available when @variables.serial_number != ""
in → serialNumber
out → found · assetId · productName · assetStatus · alreadyRegistered · warrantyActive · warrantyEndDate · contactFirstName · contactId · message

The first thing a scanned QR triggers. Returns three meaningfully different states — unknown serial, known-but-unregistered, already-registered — each with the guidance the agent needs to pick its next move.

An unknown serial is genuinely invalid rather than merely unseen, because assets are pre-created at order activation. There is no legitimate serial that isn't already in the org, so the action can safely tell the customer to re-check the sticker.

RegisterWarrantyActionWrites Asset

called by → subagent registration, action register_warranty, gated available when @variables.serial_found == True
in → serialNumber · customerName · customerEmail
out → success · needsEscalation · productName · serialNumber · warrantyEndDate · message

Four checks run before any write: the serial exists; it is not already registered; the email is well-formed; and the name and email match the Contact on the order. Email must match exactly, case-insensitively and trimmed. Name is checked loosely per nameMatches. An identity failure sets needsEscalation and returns with no DML at all.

On success: Status = Registered, PurchaseDate = TODAY, Warranty_End_Date__c = PurchaseDate.addMonths(Warranty_Months__c). It will backfill a blank Contact email but never overwrite one that exists — the order's email is the more trustworthy record.

Known simplification: purchase date is registration date. The real purchase date belongs on the Order and should replace this when the storefront lands.

GetCustomerAssetsActionRead only

called by → subagent claim_intake, action find_products, ungated (step 1 of every claim)
in → contactId · messagingEndUserId · customerEmail (all optional)
out → assetCount · coveredCount · anyWarrantyActive · singleCoveredAssetId · singleCoveredAssetLabel · assetSummary · resolvedContactId · message

Resolves the customer through three fallbacks in order: direct Contact id, then messaging end user, then email. That is what lets one action serve both the live Apple channel and a preview session with no messaging context.

The two "single covered" outputs exist to save the customer a step. When exactly one product is under warranty there is nothing to choose, so the agent skips the picker and names the product. With several, singleCoveredAssetId is deliberately null and assetSummary returns one pipe-delimited line per product, shaped to drop into an Apple List Picker.

assetCount and coveredCount are Decimal, not Integer — see §14 for why.

CreateWarrantyClaimActionWrites Case

called by → subagent claim_intake, action create_claim, gated available when @variables.defect_description != ""
in → assetId · serialNumber · defectCategory · description · contentDocumentId
out → success · caseNumber · caseId · message

The most heavily guarded action, because it is the one that creates an obligation on the business.

  • Resolves the asset by id first, then by serial. Refuses if neither identifies a product.
  • Refuses unless WarrantyDesk.warrantyActive passes, and the refusal message tells the agent to offer paid repair rather than improvise.
  • Coerces defect category to Other if it isn't one of the five valid values, so a hallucinated category cannot produce a bad picklist write.
  • Rejects a description under 15 characters — a rep cannot triage "broken".

The Case is built with the asset's Contact and Account copied down, a subject assembled from product, serial and category, and Claim_Stage__c = 'Under Review'. Photo linkage via ContentDocumentLink sits in its own try/catch: a failed file link must not lose an otherwise valid claim. CaseNumber is re-queried after insert because it is an auto-number the insert does not return.

GetClaimStatusActionRead only

called by → subagent claim_status, action look_up_claim, ungated
in → caseNumber · contactId · messagingEndUserId
out → found · claimCount · caseNumber · claimStage · defectCategory · productName · filedOn · pickupSlot · claimSummary · message

Looks up by quoted reference first, falling back to conversation identity. The reference is stripped to digits and matched with a trailing LIKE, so "CLM-00042", "claim 42" and "00001026" all resolve to the same case.

Every query is scoped Claim_Stage__c != null, which keeps ordinary support cases out of warranty answers even while the record type is invisible.

SchedulePickupActionWrites Case

called by → subagent pickup_scheduling, action book_pickup, ungated
in → caseNumber · pickupSlot (DateTime)
out → success · caseNumber · confirmedSlot · message

Books the window chosen from Apple's Time Picker. It acts only on a claim already at Approved-Pending-Pickup — booking collection for an undecided claim would be a promise the business has not made — and rejects a slot in the past. On success it writes the timestamp and advances the stage to Pickup Scheduled.

Serial scheme

Serials are SN-{OrderNumber}-{seq}, where seq counts every individual unit across all line items — a line with quantity 3 produces three assets with three serials. Order 00000100 with two single-quantity lines produced SN-00000100-1 and SN-00000100-2.

The scheme is intentionally derivable rather than random. A customer reading a serial off a nameplate can be checked against an order without a lookup table, and a rep seeing a serial immediately knows which order it came from.

The deep link

This is the piece the Apple-only decision simplified. The QR encodes the Apple URL directly, with no redirect page in between:

https://bcrw.apple.com/urn:biz:45b81efd-1d6e-405a-9547-7d8e8c34b8a8
    ?biz-intent-id=register_warranty
    &body=Register%20warranty%20SN-00000101-1

biz-intent-id tags the conversation's origin for Apple-side analytics. body is the pre-filled message the customer taps send on — which is why the QR can be skipped in testing simply by typing that string.

The QR image is generated at email time by an external chart service, quickchart.io/qr at error-correction level Q, 200px, embedded as an <img> in the HTML email. Zero code, and the recipient's mail client fetches it. The trade-off is a runtime dependency on a third party for image rendering; swapping to a generated PNG attachment is a contained change inside qrImageUrl(). The email also carries a plain tap-through link beside each QR, which costs nothing and rescues anyone reading mail on the same phone they would otherwise scan with.

Email sending is wrapped in a try/catch that logs and swallows. A deliverability setting or a missing address must not roll back asset creation — the assets are the durable artifact and the email can be resent.

System instructions

Six rules sit above everything, each mapped to a specific failure mode rather than written as general politeness:

  • Two jobs only — register warranties, file claims. Bounds the surface.
  • Every fact must come from an action result. The direct counter to a warranty agent inventing a coverage date.
  • Never say something was registered, filed or booked unless the action returned success. Added in v3 after the agent announced a claim it had not filed.
  • Never call an action with an empty value for something the customer told you. Added in v4 after the agent called a lookup with an empty email and reported a false negative.
  • Never approve, reject or predict a claim outcome. The commercial guardrail.
  • Two or three sentences. The output is a text message on a phone, not a support email.

The variable rule, learned the hard way

A variable is the right home for a value only when an available when guard depends on it. Otherwise it is one more step the planner can skip, and skipping it degrades silently. Machine identifiers the model must never invent — a record id like claim_asset_id — stay in variables and are written only by action outputs. Everything the customer says out loud is filled at the point of use with .... §13 shows what happened when this was the other way round.

Progress indicators

Every Apex-backed action sets include_in_progress_indicator with its own message — "Looking up that serial number…", "Filing your claim…". On a phone, a silent pause during a SOQL round-trip reads as a broken bot.

Prompt-injection posture

Three layers. System instructions forbid predicting or deciding claim outcomes. The off_topic subagent carries an explicit rule set covering instruction override, system-prompt disclosure and identity claims. And underneath both, no Apex action can approve anything — Claim_Stage__c only ever reaches Approved-Pending-Pickup by a rep, never by the agent. A customer who talks the model into agreeing they deserve approval still changes nothing.

Agent routing is exclusive

Setting RoutingType, TargetQueueId or RoutingConfigurationId alongside an agent SessionHandlerId is rejected: "Only a Queue or Flow Routing Method with Fallback Queue can be configured for this Messaging Channel." Agent routing and queue routing are mutually exclusive at channel level; the fallback queue is the only queue reference an agent-routed channel accepts. Note also that Salesforce's published checklist describes routing as "Omni-Channel flow and fallback queue, or a queue" — direct Agentforce Service Agent routing is a newer third option not yet reflected there.

§10 Security model

Access is granted through two permission sets, split by who does the work. Nothing was granted at the profile level — profiles are shared org-wide furniture, and a feature's access should be removable by unassigning one thing.

The split is not cosmetic. The Einstein Agent User license rejects several messaging and metadata permissions outright, so bundling human-agent rights into the same set would have made it unassignable to the agent. It is also the right conceptual boundary: the agent needs data access, a human needs console and presence.

§13 Defects found, and what they taught

Four live tests were needed to get registration working end to end. Each failure is recorded because each one generalises to any Agentforce build, and three of the four were my errors of design rather than typos.

SymptomCauseFix
Agent hung mid-registration. Collected serial, name and email, then said "please wait while I confirm your serial number" and never returned. Nothing written. Zero SetupEntityAccess rows — the Einstein Agent User could not execute any action class. Every prior integration test had passed as System Administrator through the REST invocable endpoint, proving the logic but not the runtime identity's ability to reach it. Eight Apex class grants. Fixed
Claim announced but never filed. Agent asked which product, asked for a category, said the claim was being filed. No Case existed afterwards. Three defects at once: the customer's product choice had no path into the action (and serial_number still held the serial from a registration earlier in the same conversation, so it would have filed against the wrong pump); the description and photo steps were skippable because create_claim was gated only on warranty_active; and nothing tied the success message to an action result. v3: separate claim-scope variables, gate on defect_description, system rule against announcing unconfirmed success. Fixed
False negative. Customer gave their email; agent replied "no products covered under warranty" when two were. The lookup was called with an empty string. A @utils.setVariables setter was supposed to record the email into a variable the action read; the planner skipped the setter and called the action anyway. v4: conversation values filled at point of use with ..., setters removed. Fixed

Two rules that came out of this

An ordered procedure written as prose is a suggestion. Anything that must happen before an action fires belongs in that action's available when, where the planner cannot route around it.

An ungated variable dependency does not fail loudly — it fabricates a plausible negative. Compare the two claim bugs: skipping remember_defect makes create_claim unavailable, so the planner hits a wall and self-corrects. Skipping the email setter blocked nothing; it produced a valid call with an empty parameter, a technically true "nothing found", and a confident wrong answer to the customer. That is the more dangerous shape of failure.

§14 Platform constraints encountered

This build ran entirely through REST, Tooling and Connect APIs — no CLI, no metadata zip deploy, no UI session. Several platform behaviours only surface under those conditions. Each one cost real time and each will recur.

ConstraintResolution
Tooling API cannot create a BusinessProcess. The Metadata complexvalue rejects description as a scalar (JSON_PARSER_ERROR) but creation fails without it ("Property 'Description' is not initialized in the framework"). A closed loop.Sidestepped. Tooling requires a business process for a Case record type; standard REST POST /sobjects/RecordType does not.
RecordType.IsActive is not writeable on create via standard REST.Omit it — record types are created active.
UserInfo.getSessionId() throws in this API session context, so Apex cannot reach the org's own SOAP Metadata API. The Visualforce $Api.Session_ID workaround also fails, at compile: "the return value of Session.getSessionKey() is null".Abandoned. There is no session to borrow.
The headless metadata bridge covers almost nothing. /headless/metadata accepts only named-child types inside a CustomObject wrapper. Profile, PermissionSet, Flow, GenAiPlannerBundle, BusinessProcess and MessagingChannel all return UNSUPPORTED_OPERATION on create and update, at both v63 and v67.This is why record-type profile visibility and presence-status access remain manual. It also ruled out the Metadata API for the agent — Next-Gen Authoring turned out to be the better surface anyway.
ApexClass cannot be PATCHed directly — INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITY.Use the container flow: MetadataContainer → one ApexClassMember per class → ContainerAsyncRequest → poll State until Completed.
Agent Script rejects Apex Integer outputs. Publish fails demanding object type with complex_data_type_name: lightning__integerType.Changed the three count fields to Decimal, which maps cleanly to Agent Script number. Immaterial to a chat response.
Agent Script validation only runs at publish. The /validate endpoint wants an agentJsonString and reports "Agent Script is null or empty" for a stored bundle version.Publish is the validator, and it returns precise actionable errors.
Channel IsActive is not directly writable for an externally-provisioned channel. Salesforce's own MIAW guidance says to flip the field with a record update, which works there — the validation is specific to channels whose activation involves a handshake with an outside platform. Tooling 404s, the metadata bridge refuses, and PATCH /connect/livemessage/channels returns 204 and changes nothing.Unresolved by API. Setup UI — §15.
ServicePresenceStatusAccess is not an addressable sObject in the Data or Tooling API, and lives as a sub-element of PermissionSet metadata, which the bridge also refuses.Manual, or deploy the permission set from metadata (§16).
The Einstein Agent User license refuses View All permissions, and MCPMetadataApi / ModifyMetadata.Removed View All entirely — the right answer regardless.
ConfigureLiveMessage and ViewSetup have hard permission dependencies (CustomizeApplication, ManageCustomPermissions, ManageTranslation, ViewRoles).Added ViewRoles alongside ViewSetup; left ConfigureLiveMessage to the admin profile.

§15 Gaps and manual steps

Two clicks, each blocked by a documented API refusal

  1. Grant presence status access. Setup → Permission Sets → WarrantyDesk Support Agent → Service Presence Statuses Access → add Available - Messaging. Without it nobody can go available and escalations queue forever.
  2. Grant Case record type visibility. Setup → Profiles → System Administrator → Record Type Settings → Case → move Warranty Claim to Selected.

Channel activation — done

The Apple Messages channel was activated through the Setup UI on 31 Aug 2026. That is worth more than one checkbox: because activation involves a handshake with Apple, a channel that activates proves the Apple-side chain is complete — Messaging Platform set to Salesforce Messaging in Apple Business Register, Apple's approval granted, and the messaging service provider connection tested. None of that is readable from the API, so activation succeeding is the only evidence available that it all landed.

Known gaps, ranked

  • No Apex test coverage. Blocks any path to production.
  • Rep side not built. Approval process, the approve/reject decision, and the notification flow that fires the approved / rejected / resolved messages back into the Apple thread.
  • Photo capture is declared but unwired. CreateWarrantyClaimAction accepts a contentDocumentId and links it, but nothing passes the ContentVersion id from an Apple attachment into the action. The conversation asks for a photo; nothing verifies one arrived.
  • Claim intake unproven end to end. Registration passes on v4; the claim path and especially the multi-product picker have not been re-tested since the v4 fix.
  • Purchase date is registration date. Resolved when the storefront supplies a real order date.
  • Serial uniqueness is trigger-enforced only.
  • No Messaging Session record page. Zero FlexiPages target that object, so reps get the standard layout. On Salesforce's checklist as a recommended item.
  • QR rendering depends on an external service. Contained inside qrImageUrl().

Deploying the permission sets solves two manual steps

Apex class access (<classAccesses>) and presence status access (<servicePresenceStatusAccesses>) are both sub-elements of PermissionSet metadata. Neither could be created through the APIs available in this session, but both deploy normally with the permission set — so retrieving and redeploying these two components through the CLI is the API-free route past the presence-access click in §15.

What this package does not and cannot carry

  • Permission set assignments and license assignments — data, not metadata. Re-assign after deploy.
  • Queue members and PresenceUserConfigUser membership — data.
  • Record type profile visibility — lives in Profile metadata, deliberately excluded here because deploying a whole profile between orgs is destructive.
  • Channel activation state and the Apple-side provider connection.
  • Test data — accounts, contacts, products, pricebook entries, orders, assets.
  • The consent keywords — MsgChannelLanguageKeyword is channel data created at channel creation.

§17 Next: the Experience Cloud storefront

v2 replaces API-seeded orders with a real storefront — an Experience Cloud site with a React front end where customers buy a product and receive the QR email. Recording now what that changes, while the reasoning is fresh.

What already supports it, unchanged

The entire warranty chain hangs off Order.Status = 'Activated'. It does not care whether the order came from the API, a screen flow, or a React checkout. OrderWarrantyTrigger, asset minting, the serial scheme, the QR email and every agent action work as-is the moment a real order activates.

This was the point of seeding orders by API rather than building a storefront first: the mechanism was provable without the presentation layer.

What the storefront must supply

RequirementWhy it matters
A logged-in Contact on the order — BillToContactId or ShipToContactIdLoad-bearing. OrderWarrantyService copies it onto every Asset, and the entire identity model in §2 depends on the asset being born linked to a real Contact. A guest checkout with no Contact breaks registration verification completely.
A verified email on that ContactIt is both the QR email destination and the strict half of identity verification.
Order activation as an explicit stepAssets mint on activation, not on order creation. A checkout that leaves orders in Draft produces no warranties at all.
A real purchase dateLets RegisterWarrantyAction stop using registration date, closing the §15 simplification.

Decisions to revisit

  • Customer Community licenses and sharing. Every action is without sharing today, which was correct for an agent acting on a customer's behalf. Once real community users read their own orders, the sharing model needs a deliberate second look — community users are the case where sharing rules genuinely matter.
  • Whether the redirect page comes back. Dropped because Apple-only removed the need to branch. If Android ever needs supporting, /w/{serial} returns as the switch point — and the deep link construction already lives in one method, OrderWarrantyService.appleDeepLink(), ready to become two.
  • QR generation. The external chart service is fine for a demo. A storefront that emails customers at volume should generate the PNG in Apex and attach it, removing a third-party runtime dependency from a customer-facing email.
  • Guest access. Nothing in v1 needs a guest user profile. Keep it that way if possible — it is the largest attack surface an Experience Cloud site introduces.

The order of work that keeps risk lowest: finish proving the claim path on v4, scan a real QR on a real iPhone now that the channel is live, build the rep side, and only then replace seeded orders with the storefront. The storefront is presentation over a mechanism that already works; the rep side is missing mechanism.
