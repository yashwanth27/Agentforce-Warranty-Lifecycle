§0 How to read this

Every resource in this document is classified by the layer it belongs to. The classification matters because it tells you what kind of change each resource can absorb.

LayerMeaningExamples in WarrantyDesk
Entry pointWhere something outside Salesforce starts a chainOrder activation · QR scan · inbound Apple message
ConfigurationDeclarative setup with no logic of its own; changes behaviour by existingMessagingChannel · QueueRoutingConfig · PermissionSet
OrchestrationDecides what runs next but performs no business logicOrderWarrantyTrigger · warranty_router · Atlas planner
Business logicValidates, decides, computes, writesAll six action classes · OrderWarrantyService
Data layerWhere state livesAsset · Case · Contact · MessagingSession
Human routingMoves work to a personWarranty_Support queue · Available_Messaging

The three-level naming in Agent Script

This trips people up reading the agent, so it is worth stating once. Every agent action has three distinct names, and they are frequently different:

reasoning.actions.find_products      ← the ALIAS the planner reasons about
    ↓ points at
actions.get_customer_assets          ← the DEFINITION (inputs, outputs, target)
    ↓ target
apex://GetCustomerAssetsAction       ← the IMPLEMENTATION (Apex class)

Throughout this document, traces name all three so you can follow a call from the conversation to the SOQL.

       Source today is an API insert; in v2 it is the storefront checkout.

  Type: Apex Trigger (after insert, after update) — ORCHESTRATION

Where the QR image actually comes from

Salesforce never calls quickchart.io. It writes an <img src> into the email body; the recipient's mail client makes that request when the customer opens the email. This is why no Named Credential or Remote Site Setting exists, and why the org has no outbound integration at all.

Where validation actually happens — read this before changing anything

Two independent layers, and they are not redundant.

The script gate (available when @variables.defect_description != "") makes the action invisible to the planner. Its job is to shape reasoning — the planner cannot choose an action it cannot see, so a skipped step becomes a wall it must back out of rather than a silent omission.

The Apex guards inside CreateWarrantyClaimAction re-check everything the gate implies, plus warranty validity, category validity and description length. Their job is to hold when the model is wrong, jailbroken, or when the action is called from anywhere other than the agent — including the REST invocable endpoint used for testing.

Removing either one leaves a real hole. The script gate alone can be reasoned around by a sufficiently persuasive conversation; the Apex guard alone produces the failure documented in the reference doc §13, where the agent cheerfully told a customer their claim was filed while the Apex was refusing it.

Where conversation state actually lives

The question of state comes up most sharply here, because a booking spans several turns. There are three distinct stores and they behave differently:

StoreHoldsLifetime
Agent variablesBooleans that gate actions (serial_found, defect_description, warranty_active, claim_filed) and machine ids the model must not invent (claim_asset_id)One conversation session. Lost when the session ends.
Salesforce recordsEverything durable — Asset.Status, Warranty_End_Date__c, Claim_Stage__c, Pickup_Slot__cPermanent. This is the real state machine.
Conversation transcriptValues the planner fills at call time with ... — email, chosen serial, customer name, defect categoryThe session's message history.

OmniScript state: NOT USED. No OmniStudio in this org.

The rule that decides which store a value goes in

A value lives in an agent variable only when an available when guard depends on it, or when it is a record id the model must never fabricate. Everything else the customer says out loud is filled at the point of use from the transcript.

This was learned by getting it wrong. An ungated variable is one more step the planner can skip — and skipping it does not fail loudly, it produces a call with an empty parameter and a confident wrong answer. Reference doc §13 has the incident.

One link in this chain is not yet complete

ServicePresenceStatusAccess — the permission-set grant that lets a human actually select Available - Messaging — could not be created through any API available in this build. Until it is granted in Setup, or the permission set is deployed from metadata, an escalated conversation reaches Warranty_Support and waits there with nobody able to go available to receive it. Every other link above is in place and verified.

How the handoff works, precisely

There is no transfer of a record and no new conversation. @utils.escalate changes who is answering the existing MessagingSession — the agent detaches, Omni-Channel routes the same session as a work item, and a human takes ownership of it. Because the channel, the session and the customer's Apple thread are all unchanged, the customer experiences one continuous conversation in which the replies simply start coming from a person.

§5 Plain English

What happens when a customer scans the QR code?

The QR encodes an Apple URL, not a web page. Scanning it opens Apple Messages on the customer's iPhone with the message body already written — Register warranty SN-00000101-1 — addressed to the business ID 45b81efd-1d6e-405a-9547-7d8e8c34b8a8. That string was built by OrderWarrantyService.appleDeepLink when the order was activated. There is no redirect page and no web hop; the Apple-only decision removed the need for one.

The customer taps send. Apple delivers it to MessagingChannel APPLEBUSINESSCHAT_US_45b81efd…, which is matched by that same business ID. The platform creates a MessagingEndUser for the Apple ID and a MessagingSession for the conversation, then checks the message against MsgChannelLanguageKeyword — if the customer had typed stop or help, the platform would answer and end the session, and the agent would never see it.

It didn't, so the channel reads SessionHandlerId and hands the session to Warranty_Claims_Agent v4, running as the Einstein agent user. Three linked variables bind automatically from the session, so the agent already knows who this is without asking. The Atlas planner then validates every action across every subagent — this is where a missing Apex class grant kills the whole agent rather than one action.

The message lands in warranty_router, which does nothing but route. It sees a serial number, recognises a QR scan, and transitions to registration. That subagent calls remember_serial to put the serial in a variable, which unlocks check_serial → CheckSerialRegistrationAction. That Apex reads the Asset through WarrantyDesk.assetBySerial and reports back three things: the serial exists, it isn't registered yet, and the first name on the order.

The agent asks for a name, then an email, one question per message. Then register_warranty → RegisterWarrantyAction runs four checks before touching anything: serial exists, not already registered, email is well-formed, and — the important one — the name and email match the Contact already on the order. If they don't, it returns needsEscalation and writes nothing. If they do, the Asset flips to Registered with a purchase date and a computed end date, and the agent confirms using only values the action returned.

What happens when a customer files a claim?

The router sends them to claim_intake, which runs seven ordered steps. Step one is always find_products → GetCustomerAssetsAction, which figures out who the customer is via three fallbacks — Contact id from the session, then MessagingEndUser, then the email they give — and returns what they own and what is still covered.

What happens next depends on the count. One covered product and the action returns singleCoveredAssetId, so the agent names it and moves on. Several and that field is deliberately empty; the agent lists them and the customer picks, and the chosen serial gets filled into the claim call from the transcript. None covered and it stops — no claim is filed and the agent offers paid repair.

Then the defect category, offered as exactly five choices. Then the description, recorded by remember_defect — and this is the load-bearing step, because create_claim carries available when @variables.defect_description != "". Until a description exists the action is invisible to the planner. It cannot be skipped, only backed out of. Then a photo is requested, though nothing yet wires the file into the action.

Finally CreateWarrantyClaimAction re-checks everything server-side: it resolves the asset by id or serial, refuses if the warranty isn't active, coerces an invalid category to Other, and rejects a description under 15 characters. Only then does it insert the Case with the Contact and Account copied down from the Asset and Claim_Stage__c = 'Under Review'. It re-queries the CaseNumber, because the insert doesn't return an auto-number, and hands it back. The agent may only say the claim is filed once it has that reference in hand.

What happens when escalation occurs?

Five subagents can escalate, so the customer can ask for a person at almost any point. Each calls @utils.escalate, and the agent detaches from the conversation.

Nothing is transferred and nothing restarts. The platform reads FallbackQueueId off the channel — mandatory whenever an agent is the session handler — and routes the same MessagingSession into Warranty_Support as an Omni-Channel work item. Apple_Routing decides distribution (MostAvailable), sfdc_livemessage is the work type, and Omni looks for someone present on that channel via Available_Messaging. The work item appears in the Omni widget in the Service Console, the human clicks Accept, and takes ownership of the session that already exists.

Because the channel, the session and the customer's Apple thread are all unchanged, the customer sees no seam — the replies simply start coming from a person, in the same thread, with the full transcript visible to the rep on the MessagingSession record.

One caveat that matters operationally: until ServicePresenceStatusAccess is granted, nobody can select Available - Messaging, so an escalated conversation reaches the queue and waits there indefinitely. Every other link is in place.
